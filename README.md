# DontGetKicked — Классификация проблемных автомобилей (линейные модели)

**Цель:** предсказать, окажется ли купленный на аукционе подержанный автомобиль машиной со скрытыми проблемами, которую дилеру невыгодно перепродавать (`IsBadBuy = 1`).

---

## Вопросы исследования

1. Какая из трех моделей (LogisticRegression, GaussianNB, KNN) лучше справляется с задачей?
2. Улучшают ли нелинейные признаки (отношения цен, групповые статистики) качество линейной модели?
3. Что эффективнее для отбора признаков, ручной отбор по коэффициентам или L1-регуляризация?
4. Переобучена ли итоговая модель при проверке на тестовой выборке?

---

## Данные

**Источник:** [Kaggle — Don't Get Kicked](https://www.kaggle.com/c/DontGetKicked)  
**Размер:** 72 983 строк, 34 колонки  
**Дисбаланс классов:** ~12% `IsBadBuy = 1`

Поля:

| Тип | Примеры |
|---|---|
| Числовые (~17) | `VehOdo`, `VehicleAge`, `VehBCost`, `MMRAcquisitionAuctionAveragePrice`, `MMRCurrentRetailAveragePrice`, … |
| Категориальные (12) | `Auction`, `Make`, `Model`, `Trim`, `Color`, `Transmission`, `WheelType`, … |
| Удалены | `RefId`, `PRIMEUNIT`, `AUCGUART` (>95% пропусков), `PurchDate` (использован для сплита) |
| Таргет | `IsBadBuy` (0 / 1) |

## Методология

**Стек:** Python, `pandas`, `numpy`, `scikit-learn`

### Разбивка по времени

Данные делятся по `PurchDate` на 3 равные части, чтобы модель обучалась на прошлом и проверялась на будущем:

```
train первая треть дат
valid средняя треть
test последняя треть   (не трогается до финального шага)
```

### Препроцессинг

* Категории: `LabelEncoder`, обученный только на train; новые категории в valid/test получают код `-1`.
* Числовые пропуски: заполняются медианой по train.
* Нормализация: `StandardScaler` (fit только на train).

### Инженерия признаков (шаг 7)

Добавлены нелинейные признаки на основе существующих:

| Признак | Формула / логика |
|---|---|
| `Odo_per_Age` | `VehOdo / (VehicleAge + 1)` пробег на год жизни машины |
| `Ratio_auction_price` | текущая аукционная цена / цена на момент покупки, скорость обесценивания |
| `Ratio_retail_price` | аналогично для розничной цены |
| `Cost_vs_MMR` | цена покупки / справочная аукционная цена, переплатили или нет |
| `Make_mean_cost` | средняя цена покупки по марке (groupby по train) |

Групповые статистики посчитаны только по train, чтобы не было утечки данных.

### Метрика

**Gini = 2 × ROC AUC − 1** (реализована через трапециевидное интегрирование под ROC-кривой, совпадает с sklearn).

## Реализации

| Класс / функция | Описание |
|---|---|
| `my_roc_auc` / `my_gini` | ROC AUC и Gini через накопленные суммы (cumsum) и метод трапеций |
| `MyLogisticRegression` | SGD с mini-batch, L2-регуляризация, фиксированный random_seed |
| `MyKNN` | Векторизованный k-NN (формула `‖a−b‖² = ‖a‖² + ‖b‖² − 2aᵀb`), батчевый predict |
| `MyGaussianNB` | Gaussian Naive Bayes через log-вероятности (численная стабильность) |
| `my_precision_recall_f1` | Precision, Recall, F1 через матрицу ошибок |
| `my_auc_pr` | AUC PR через трапециевидное интегрирование под PR-кривой |

Все реализации валидированы против sklearn, результаты совпадают.

## Результаты

### Базовые модели (шаг 4, до инженерии признаков)

| Модель | Gini (valid) |
|---|---|
| **LogisticRegression** | **лучший** |
| KNN (k=25) | хуже (проклятие размерности, ~30 признаков) |
| GaussianNB | хуже (нарушение допущения о независимости признаков) |

Все три модели превысили порог Gini >= 0.15.

### После инженерии признаков (шаг 7)

LogisticRegression с нелинейными признаками показала прирост Gini по сравнению с базовой версией.

### Отбор признаков (шаг 8)

| Подход | Признаков | Gini (valid) |
|---|---|---|
| Все признаки | ~35 | baseline |
| Ручной отбор (топ-15 по коэффициентам) | 15 | чуть ниже |
| **L1-регуляризация** | авто | **лучший / сопоставимый** |

L1-регуляризация предпочтительнее: учитывает корреляции между признаками и не зависит от порядка отбора.

## Выбор метрики для задачи (шаг 12)

Для поиска «лимонов» предпочтительна метрика **F1-score** (со смещением порога в сторону повышения Recall):

* **Accuracy** не подходит: дисбаланс классов (~12%) делает её нечестной.
* **Recall** важнее Precision: пропустить «лимон» дороже, чем зря отказаться от хорошей машины.
* **F1** балансирует оба требования, не давая модели «читерить» (например, предсказывать все машины «лимонами» ради Recall = 1).
